# E4 / E5 — naval hull HP and mission-objective state

Two spikes that decide whether C4 can sink ships and whether C5 exists at all.
Both are pure RE: no code until a field is found. Same rule as everywhere else —
`[[ship+0x5C]+0x84]` and "objective complete" are not to be coded against until a
card below says PASS.

---

## E4.1 — Where is ship hull HP?

**Plan text** (`PROGRAM-PLAN.md:334`): *"Hull HP must be found, not guessed. The
`[[ship+0x5C]+0x84]` value regenerates +6/tick and is not health **[D]**;
`ShipHealthData` exists as a class **[D]**. Spike: enumerate services on a live
ship, diff a damaged vs undamaged ship, find the setter."*

Known and do **not** re-derive:

* `[[ship+0x5C]+0x84]` is **disproven** — it regenerates +6/tick and is not health
  (`PROGRAM-PLAN.md:334`; `DECOMP-AUDIT.md:92` — *"not found by any decomp search;
  that field is the regenerating value we already rejected"*);
* `ShipHealthData` exists as a class (`PROGRAM-PLAN.md:334`);
* the ship is a second avatar; the ghost ship is a render clone only and must never
  get a physics body (`PROGRAM-PLAN.md:328-332`);
* the current build crashes on world travel (`PROGRAM-PLAN.md:337`).

| | |
|---|---|
| question | which field is the ship's hull HP, which function sets it, and does it stay put when the ship is damaged? |
| cost | 3 sessions |
| kills | ships that can sink |

**Procedure (one session per pass).**

1. Take control of the Jackdaw in open water; log the ship entity VA, its vtable,
   and `ship+0x5C` (now believed `World`, not a health service —
   `COOP-MASTER-PLAN.md:127`).
2. Enumerate the services reachable from the ship entity, the way `PLAN-v2.md:21-23`
   does for NPCs (`ai+0x5C` count `+0x62`, `ai+0x70` count `+0x76`): dump base,
   count, each service's vtable and class id. Flag anything whose class is
   `ShipHealthData`.
3. Snapshot every u16/u32 field of the candidate services; fire one cannon volley
   into the hull from a gunboat; re-snapshot. Keep only fields that changed.
4. Repeat with a *different* damage amount and a **repair** (or a fresh ship) so
   the +6/tick regenerator is excluded by the second diff.
5. Set a hardware write breakpoint on the surviving candidate and confirm the
   setter fires on the hit, not on the tick.

**What to log.** `session, tick, shipVA, serviceIndex, vtable, classId, offset,
valueBefore, valueAfter, delta, writerVA`. Header with the ASI hash. One row per
candidate field per volley — the +6/tick field must appear and be labelled
`rejected: regenerator` so the next reader does not rediscover it.

**PASS.** A field that (a) drops by an amount consistent with the cannon damage,
(b) does not rise on its own between volleys, (c) is written by an identified
setter, and (d) reaches a terminal value on a sink. Report the offset and the
setter VA.

**FAIL / INCONCLUSIVE.** More than one field survives the second diff, or the
value moves with no damage. That is INCONCLUSIVE, not a partial PASS — C4 gate
check 1 allows *"≤ 1 unit error"* (`GATES.md:108`), so a field we are unsure of is
a gate failure later.

**Kill criterion.** 3 sessions with no storage location ⇒ *"ships are unkillable
and C4 is boarding-only"* (`PROGRAM-PLAN.md:334`; `PROGRAM-PLAN.md:443`). C4 gate
checks 2 and 3 (sink, boarding) then drop out; boarding and world travel stay.

**UNVERIFIED:** the field, the setter, and whether hull HP is per-ship-entity or
held in a shared fleet/naval-manager object. The service enumeration in step 2 is
what settles it.

## E5.1 — What object holds objective completion?

**Plan text** (`PROGRAM-PLAN.md:356`): *"RE spike: mission state. Find the object
that answers 'is objective X complete'. Start from
`DominoSpawningSpecification`/`Mission*` classes named in `CODE-MAP.md`, and from
what changes in memory when an objective ticks."*

Known and do **not** re-derive:

* saves are per-account and encrypted (`PROGRAM-PLAN.md:350`);
* mission logic is Domino — a condition/operator graph (`PROGRAM-PLAN.md:351`);
* *"nothing about the mission-state container is known"* (`PROGRAM-PLAN.md:351-352`);
* objective journal design is a grow-only set of `(missionId, objectiveId)`
  (`PROGRAM-PLAN.md:357`) — that design is downstream of this experiment.

| | |
|---|---|
| question | which object answers "is objective X complete", and what changes in memory at the tick? |
| cost | 5 sessions |
| kills | C5 |

**Procedure (one session = one objective tick, watched).**

1. Open the IDB on the classes named in `CODE-MAP.md`
   (`DominoSpawningSpecification`, `Mission*`); list their instance sizes and the
   vtable slots that look like queries.
2. Start a story mission whose first objective is a single action (a scripted kill
   or a reach-point). Snapshot the Domino objects and the mission manager before
   the action.
3. Complete exactly one objective. Re-snapshot: diff all u32/pointer fields of the
   Domino objects and the mission manager.
4. Set a hardware write breakpoint on each field that flipped and attribute the
   writer; keep only fields whose writer is in the Domino/condition path.
5. Repeat on a second objective in the same mission, then on the same objective
   after save/load, to prove the bit is persistent and not a transient.

**What to log.** `tick, missionId, objectiveId, objectVA, offset, valueBefore,
valueAfter, writerVA, event` — `event` ∈ {snapshot, objective_tick, save, load}.
Header with the ASI hash. Include the Domino node ids you saw tick so the journal
key `(missionId, objectiveId)` has a source in the binary, not in the UI.

**PASS.** A storage location that flips exactly once per objective completion,
per machine, and is still set after save/load. This is what M5 check 1 and check 3
measure — *"each objective completes exactly once per machine"* (`GATES.md:125`)
and *"journal identical after save/load"* (`GATES.md:127`).

**FAIL / INCONCLUSIVE.** The only thing that changes is UI/string state (`sub_13DD550`
style) and not a data field — that is INCONCLUSIVE and means the state is derived;
say so rather than coding against a string.

**Kill criterion.** 5 sessions without a storage location ⇒ *"C5 is deferred"*
(`PROGRAM-PLAN.md:356`; `PROGRAM-PLAN.md:444-445`), and the product becomes
"co-op free roam + combat". Do not stretch this to a sixth session by halves —
deferral is the cheap outcome.

**UNVERIFIED:** where the container lives, whether the graph stores per-node
completion or a single mission bit, and whether completion is mirrored in the
encrypted save. Steps 3–5 settle the first two; the save question is answered by a
load and a re-read.
